# Mixer selection, groups and saved recipes

Development contract: project schema23, profile1..5 accepted (profile5 when a
typed `mixerGroup` UUID is stored). Exact executable discovery is authoritative.
This source guide does not establish a packaged release, audio qualification,
native desktop input, hardware, listening or FL Studio familiarity acceptance.

F9 opens Mixer. Click a strip name to select its stable insert as the active
source. Ctrl-click names toggles multiple selection; Shift-click names selects a
range in current display order. Ctrl+A selects every strip. Multi-selection and
its anchor are workspace state, not project history or saved data. Routing
footer clicks remain destination actions; they do not redefine the active
source. F2/middle-click rename normally; F2 with multiple names uses a numbered
prefix in display order. Context > Selection and groups provides bulk colour,
new/assign/select/dissolve group, group marker colour, group mute and solo.
Alt+G opens New group. Cancel applies nothing. Dialog/menu targets are pinned to
the project session, revision, selection and active source; reopen stale intent.

Groups are display/selection metadata, **not buses**. Route explicitly through
existing routing operations. Master may be selected/renamed/coloured; it cannot
belong to a display group. Each other insert belongs to at most one group.
Assigning selected members explicitly moves membership from their former groups;
empty groups remain addressable until dissolved. Dissolving removes metadata,
never inserts, channels, routes, effects or automation. Every document operation
is one shared history edit; an owned `vibera_gesture` can group/cancel a sequence.

`vibera_mixer action=state` returns `organisation`; `vibera_state` returns the
same state as `mixerOrganisation`. Read `selected`, `active`, `anchor`, groups
and stable UUIDs. Use `selectMany` with exact stable `ids` (not rows), a
replace/add/remove/toggle/range mode and optional active member. `selectGroup`
takes a group UUID; an existing active source is retained when it is a member,
otherwise the first group member in current display order becomes active.
`selectAll` needs no identity. Read-only state is available during edit ownership.

Discover document arguments via `vibera_commands`:

```json
{"command":"mixer.group.create","args":{"ids":[1,3],"text":"Drums"}}
{"command":"mixer.group.assign","args":{"ids":[2],"mixerGroup":"<actual32hexUUID>"}}
{"command":"mixer.group.assign","args":{"ids":[2],"mixerGroup":""}}
{"command":"mixer.group.rename","args":{"mixerGroup":"<actual32hexUUID>","text":"Percussion"}}
{"command":"mixer.selection.rename","args":{"ids":[1,3],"text":"Drum"}}
```

Names are trimmed, without tabs/newlines; group names are case-insensitively
unique (1..64 characters), bulk prefixes1..55. Colour is theme0 or an opaque
ARGB integer0xff000000..0xffffffff. Marker colour preserves each strip's own
colour. Group context adds **Apply this insert colour to group** for an explicit
source colour, or **Reset group insert colours to theme** when its stored colour
is0. Both invoke canonical `mixer.group.colourMembers` with the exact group UUID
and original clicked stable member ID as `mixer`. It copies stored ARGB, never a
screen pixel or global theme;0 resets each member's own default presentation,
which need not render as identical RGB. Marker colour, group membership,
selection/active source, names, routes, sends, effects and solo/mutes are retained.
The operation has one Undo and exact owned-gesture cancel; already matching
colours are a no-op. Missing or nonpositive source IDs fail MCP schema validation
with `invalid_arguments`; a positive ID absent from the project gives
`mixer.group.invalidColourSource`. A source outside this group gives
`mixer.group.nonMemberColourSource`. Closed/stale menu intents never retarget.

```json
{"command":"mixer.group.colourMembers","args":{"mixerGroup":"<actual32hexUUID>","mixer":1}}
```

Discover its required fields via `vibera_commands`. Inspect actual member
`index`/`colour` through `vibera_inspect entity=mixer`; organisation readback's
`colour` remains the separate group marker. Saved macros retain explicit UUID
and member ID with `currentContext=false`; context macros resolve the active
member/group at run time. Profile5 already serializes both, without a new schema.
This is a canonical colour target update, not native graph/audio completion.

New group UUIDs are generated by the application, persist across
save/reopen/Undo/Redo and are never accepted as names or list offsets. Re-read
targets after project replacement. Invalid IDs/names/colours/membership fail
before document mutation, with typed `mixer.group.*` errors.

Group Solo retains all members and their downstream paths; Solo connected also
retains upstream inputs. Switching single/group solo preserves the first mute
baseline. Unsolo restores that baseline by default, or follows the Workflow
restore-mutes preference; explicit `restore=false` unmutes all. **Manual insert
or group mute/unmute ends solo restoration ownership while retaining the newer
actual mask.** A later stale group Unsolo refuses rather than overwriting newer
mutes. Undo can recover the original solo session. Membership changes are
unavailable while a group owns solo; restore it first. Project files retain
group solo's exact baseline. This is canonical target completion, not DSP ramp
settling or proof of heard audio.

## Saved recipe configuration and actual execution

Use `vibera_macros action=state, includeSchemas=true` to discover the actual
Customization-supported canonical commands, explicit/current-context argument
schemas, recipes and **generation**. This service does not edit keybindings or
other settings. It factors the existing authoritative macro eligibility rule;
it does not pretend every accepted recipe is available in every runtime context.
Existing command prerequisites, worker/routing admission and history failures
remain authoritative. Some inherited command schemas accept broader fields;
that is not a promise of native widget control or full legacy MCP coverage.

Create/update requires `{action,generation,macro:{id,name,steps}}`. Use stable
`macro.*` IDs and1..64 `{action,parameters,currentContext}` steps. `currentContext`
defaults true; explicit false pins supplied stable targets. Context group creation
passes its new UUID to following context group steps. Recorded new group/bulk
actions retain their exact explicit targets instead of silently retargeting a
different selected group. Use state includeSchemas to obtain actual valid
argument ranges/defaults; no simulated keys or mouse input is needed.

```json
{"action":"create","generation":"<state generation>","macro":{
  "id":"macro.drumGroup","name":"Group selected drums","steps":[
    {"action":"mixer.group.create","parameters":{"text":"Drums"},"currentContext":true},
    {"action":"mixer.group.colour","parameters":{"value":4285610968},"currentContext":true}
  ]}}
```

Settings Macro Save/Run/Delete and MCP use the same staged Customization
validator, persisted application service and content generation. Success for
create/update/remove requires actual atomic profile replacement and in-memory
publication; it is not an accepted write request. Exact external profile bytes
and current settings contribute to generation. Stale tokens, corrupt profiles
or divergent saved/current settings refuse, preserving both copies. Reconcile
explicitly through Settings before retrying; do not loop destructive retries.
This is optimistic content checking, not an OS transaction against arbitrary
concurrent third-party writers. A committed-but-readback-failed error explicitly
says configuration was committed; inspect state before another mutation.

Run only an actually saved current recipe using `{action:"run",id,generation}`.
The real runner applies its synchronous musical steps in one checked history
transaction, rolling back an ordinary failed step. `completionScope` is canonical
history, never native graph/audio readiness. Existing Channel-routing-only
recipes expose their real pending `operation`/`routing`; poll `vibera_mixer
action=routingJob` until completed/failed. Published routing is too late to
cancel; use checked Undo after completion. Mixed routing/content remains the
existing explicit refusal. UI drafts are discardable before Save; settings
configuration itself is not project Undo. Recipe runs use actual musical Undo.

`state id=...` returns an editable recipe whose steps roundtrip through update.
After successful config mutation re-read/use the returned generation. `remove`
requires exact ID and generation. `profileExists`/`profileMatchesMemory` and
`configurationCommitted` distinguish persistence; `dspSettlingAcknowledged`
remains false. No provider/model-specific client or proprietary FL assets used.

## Insert membership (development source)

Use the Mixer effect menu's **Create insert**, **Delete unused insert**, or
explicit **Delete and reroute to** confirmation. Equivalent canonical commands:

```json
{"command":"mixer.insert.create","args":{"text":"Percussion bus"}}
{"command":"mixer.insert.delete","args":{"mixer":19}}
{"command":"mixer.insert.delete","args":{"mixer":19,"mixerDelete":{"replacement":0,"removeEffects":true,"removeAutomation":true,"removeGroupMembership":true}}}
```

Discover schemas from `vibera_commands`; never assume the example19 exists.
Creation appends a neutral strip routed to Master; the18 defaults remain and
the limit is Master plus128 inserts. IDs are stable within the project and
session-reserved across cancellation and Undo branches. A reopened snapshot has
a new project identity and reservation session; abandoned IDs are not globally
reserved forever. Display positions are not IDs.

Deletion refuses assigned Channels/incoming sends unless a surviving replacement
is explicit, preserving send levels and rejecting self routes, duplicate sends
or cycles. Removing effects, automation links/initial values and display-group
membership each requires its own explicit permission. Curves, notes, placements,
unrelated targets and controller profiles are not silently deleted. Master is
protected; active solo must be restored first. Organisation readback includes
references and model eligibility, not a guarantee that current recording,
gesture, native control or file ownership permits execution.

These are asynchronous structural operations, unavailable in macros/gestures.
The returned exact `insertCreate`, `insertDelete`, or `insertHistory` operation
is polled using `vibera_mixerchain action=job`; cancel only that owned operation
before publication. Undo/Redo returns the same service's history job. A pending
reply is not completion. Brief structural interruption is accepted; completion
requires actual activation/recovery, or `deferredNoDevice` without pretending
playback is active. Refusals preserve canonical data/history; post-publication
activation failure retains the undoable intended change and reports recovery.
Current source/runtime qualification is recorded in STATUS/VERIFICATION, not
established by this guide. Full Mixer/DAW and legacy MCP consolidation remain open.

Trim unused tracks: action `mixer.trimUnused` (Mixer track menu > Trim unused tracks (N))
deletes, highest index first, every insert that the ordinary `mixer.insert.delete` accepts with
its default policy and that has no effects (no Channel, incoming route, automation or group
reference; Master stays). Each deletion runs through the normal insert lifecycle after the
previous one settles, so it is one Undo step per track. Status ends with
"Trimmed N unused Mixer track(s)".
